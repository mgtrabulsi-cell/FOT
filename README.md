# GameWire

A responsive NFL hub with live scoreboards, weekly matchups, player statistics, and a favorite-centered feed called Your Locker Room.

## Run locally

Install Node.js 20 or newer, then run:

```sh
npm install
npm run dev
```

Open the local URL printed by Vite. `npm run build` creates a production build.

The VS Code task **Start GameWire dev server** is also configured for launching the app.

Desktop views use an 85% interface scale, with a compact matchup scoreboard and larger player names and headshots in The Wire, Stat Hub's player directory, and player cards. Stat Hub retains its extra player-area emphasis. Screens 760px wide or narrower keep the unscaled mobile layout.

Desktop account profiles have an additional 130% scale, larger text and form controls for readability, and single-column settings on narrower desktop screens. Mobile profile sizing is unchanged.

Locker Room uses an additional 120% desktop scale for easier reading, slightly less than the profile screen. Mobile Locker Room sizing is unchanged.

The original navy-blue theme uses bold crimson (`#cc2633`) for selection indicators, live accents, and Stat Hub chart bars. Filled red controls use a deeper crimson with white labels for readability; official team colors remain unchanged.

Player cards use slimmer per-game chart bars. Wide receiver and tight end cards include Targets in the draggable stat wheel, using ESPN's game box-score values and retaining unavailable values rather than estimating them.

The Wire omits the large page title, description, and normal feed-status label on desktop and mobile, keeping a compact date/week row immediately below navigation so games and stats appear sooner. Feed warnings remain visible.

On mobile, The Wire player box scores place each player's labeled stats on one compact horizontal row, with all stats visible without scrolling or wrapping into another row. Player identity stays above that row. The compact scoreboard uses stacked team rows with logos and names on the left and scores on the right. Stat Hub remains unchanged: its player-popup stat types retain a single horizontally scrollable, draggable row with touch-sized controls and a chart that fits the dialog width. The game selection wheels remain horizontally draggable.

The Wire's team/game search and Stat Hub's NFL player/team search open from a compact search icon in the top banner, with separate queries for each view. Clicking outside, moving keyboard focus outside, Escape, or closing the search clears the input text but preserves the active results on the page. Reopening starts with a blank field; typing a new search replaces the previous filter. The active-filter indicator remains visible, and the clear action resets both the field and results, even when the field is already blank.

Mobile browsers and Median apps (760px wide or narrower) share the same website bottom bar for The Wire, Stat Hub, LIVEWIRE, and Locker Room, including identical Lucide icons, labels, colors, and spacing. The logo, search, and account controls stay at the top; desktop browsers keep the tabs at the top. Navigation renders only inside the main app after sign-in or Continue as guest, never on splash, login, password recovery, or account-deleted screens. The bar reserves content space and respects device safe areas. Keep Median's Bottom Tab Bar Default Mode **Hidden** in App Studio; the embedded bridge also disables native tabs at startup to prevent duplicates in older wrappers. Section links use `#wire`, `#stat-hub`, `#livewire`, and `#locker-room`; game/post notification links remain supported. Rebuild existing wrappers to apply the hidden startup default; on-device iOS/Android verification is still required.

On mobile, pull down at the top of the main app until **Release to refresh** appears, then release to reload the current section. The indicator appears only during the gesture or refresh; there is no refresh button or reserved space while idle. Short pulls, horizontal swipes, form controls, and nested scrollable panels do not trigger refresh. Offline attempts show a reconnect message without reloading. Refresh uses the normal saved-first startup and background revalidation; it does not clear saved data or force a splash on every data update.

The Wire and Stat Hub game wheels both show color-coded TNF, SNF, and MNF badges for primetime games, identified by kickoff time in Eastern Time.

Favorite NFL teams keep the order set in **Locker Room → Following → Teams**. Use the up/down controls to reorder them; the top team’s matchup is featured when it is live, or when no other NFL game is live. Once that matchup is final, the next later primetime game in the selected week is featured.

Before kickoff, Player Box Score hides category filters and offers **Total stats** (default) and **Avg stats** below the Player Box Score/Team Comparison tabs. Live and final games restore All, Offense, Defense, and Special Teams, with unrestricted individual game box scores. Player Box Score omits the team-total row beneath every player group in all game states; Team Comparison is unchanged.

Pregame Player Box Score can show season-to-date totals or per-game averages for the selected team. Avg stats divides every statistic, including touchdowns and fumbles, by the player's games played (`GP`); GP itself remains a count. Missing totals or invalid GP remain unavailable. Switching modes does not fetch data again. Live and final box scores remain game-specific.

Desktop pregame tables share fixed column widths across passing, rushing, and receiving, aligning player names, games played, yards, and touchdowns vertically. Unused stat slots stay blank rather than implying a value; mobile hides those slots and keeps the labeled stat grids.

The final column shows QB interceptions (`INT`), rushing fumbles in Rushing, and receiving fumbles in Receiving (`FUM`), not fumbles lost. Missing fumble data remains unavailable. Player portraits retain ESPN's full-resolution images with top-centered framing and larger desktop headshots.

Pregame QB passing stats omit sacks per game. Live and final box scores retain the sacks reported by ESPN.

Select a player's name in The Wire's pregame Player Box Score to open the same player card as Stat Hub, with position-specific draggable stat tabs, recent-game charts, and a favorite toggle. Closing the card keeps the current matchup and team selection.

## Deploy to GitHub Pages

The [deployment workflow](.github/workflows/deploy.yml) builds and publishes the site on pushes to `main`, or when run manually. It uses Node.js 22, installs from the lockfile with `npm ci`, and gets the asset base path from GitHub Pages automatically. Local development keeps relative asset paths; project Pages uses `/FOT/`, while a configured custom domain uses its Pages base path.

1. In the GitHub repository, open **Settings → Pages** and select **GitHub Actions** as the build and deployment source.
2. For accounts and synced favorites, add these **repository secrets** under **Settings → Secrets and variables → Actions**:
   - `VITE_SUPABASE_URL`: your Supabase project URL.
   - `VITE_SUPABASE_PUBLISHABLE_KEY`: your public publishable key. Alternatively, use `VITE_SUPABASE_ANON_KEY` for the legacy anon key.
   - `VITE_VAPID_PUBLIC_KEY`: optional public VAPID key, if you configured mobile push notifications.
3. Complete the Supabase schema setup described below. In **Supabase → Authentication → URL Configuration**, set the production Site URL to `https://mgtrabulsi-cell.github.io/FOT/` and add that exact URL to the allowed redirect URLs. Keep `http://localhost:5173/` allowed for local development. If using a custom domain, use its URL instead.
4. Commit and push your changes to `main`. In **Actions**, watch **Deploy to GitHub Pages**, or select **Run workflow** to redeploy the committed version.
5. Open `https://mgtrabulsi-cell.github.io/FOT/` after deployment succeeds. Test sign-in, email confirmation/password reset, and mobile notifications if enabled.

GitHub Actions does not read your local `.env.local`; configure the repository secrets before deploying, and rebuild after changing them. Without Supabase configuration, guest browsing is available but accounts and synced favorites are not. Notifications additionally require the Supabase functions and scheduled poller described below; GitHub Pages only hosts the frontend.

Choosing **Continue as guest** loads the live scoreboard and stats without signing in, including when Supabase accounts are configured.

All `VITE_` values are public in the built JavaScript, even when supplied through GitHub secrets. Never put a Supabase service-role/secret key, private VAPID key, or cron secret in them. Local environment files remain gitignored.

To verify the project-path build locally in PowerShell:

```powershell
$env:VITE_BASE_PATH = '/FOT/'
npm run build
npm run preview -- --host 127.0.0.1
Remove-Item Env:VITE_BASE_PATH
```

Open `http://127.0.0.1:4173/FOT/`. Assets, the web app manifest, and the notification service worker stay within the deployed path. This static deployment does not require a Node.js server.

## LIVEWIRE views

Draft recovery failures do not lock the composer or disable post editing. A failed restore leaves the stored copy untouched and pauses automatic saving until restoration succeeds or the admin explicitly replaces/discards it. The editor remains usable with a visible warning and restore/save retry controls. Mobile photo attachments restored as Blobs are converted back into uploadable Files. Storage operations time out after five seconds so a suspended or blocked database cannot permanently stall later drafts.

Admin composers automatically retain one unpublished draft per account on the current device in IndexedDB, including title, body, source link, themes, edit target, and selected photo files. Returning to LIVEWIRE or reopening the site restores it after sign-in. Drafts are not uploaded until publishing and are not synced across devices; browser storage clearing/eviction can remove them. Publishing or explicitly discarding clears the draft. Editing another post asks before replacing unfinished work. Storage failures appear in the composer. Account deletion removes its draft and prevents late writes from recreating it.

Published photos open in an in-page modal with a larger, contained image instead of a new browser tab. Close with the Close button, Escape, or the backdrop; focus returns to the photo button and background scrolling is locked while open.

Apply [`supabase/livewire-views.sql`](supabase/livewire-views.sql) after the LIVEWIRE schema and before deploying the view-count UI. Each post displays its shared view count. Guests, members, and admins count equally; the count increases when any part of a post enters the visible viewport, again after scrolling away/back, reopening LIVEWIRE, or returning to the visible browser tab. Feed polling, editing, and loading older posts do not recount posts that remain visible. Posts below the fold or in hidden tabs do not count. Offline appearances are not uploaded later, but a still-visible post counts on reconnect. Totals start at zero when installed; historical views cannot be reconstructed.

The signed-in LIVEWIRE owner is the exception: that account counts once per post across devices and repeat visits. Other admins, members, and guests retain the repeat-impression behavior above. Reapply [`supabase/livewire-views.sql`](supabase/livewire-views.sql) to enable this server-side rule; no frontend update is needed. A private owner/post receipt prevents duplicate increments, with post-row locking for concurrent devices. Receipts are removed automatically when their post or account is deleted. Existing totals are retained: prior owner views cannot be identified retroactively, so the first owner view after this update can add one more. Signed-out visits are guests and cannot be identified as the owner.

The anonymous/authenticated increment RPC performs an atomic increment without granting clients permission to overwrite totals or edit posts. Apart from the private owner/post deduplication receipt, it stores only aggregate counts, not device identifiers, IP addresses, or other viewer accounts. These are impressions, not unique viewers or fraud-resistant analytics: repeat visits and scripted requests can increase them. Failed writes are logged and shown in LIVEWIRE rather than displaying a fabricated increment. Run [`supabase/tests/livewire-views.sql`](supabase/tests/livewire-views.sql) for rollback-only database validation and `node --test scripts/livewire-views.test.mjs` for visibility lifecycle tests.

## Offline access

After opening the production site online once, GameWire saves its app shell for offline launches, including from a phone's Home Screen. Once the offline worker controls the page, it proactively saves the displayed NFL week's game summaries, both teams' player/season stats, recent-game sources, team logos, and player faces, even for games and team tabs you have not opened. It repeats every five minutes while open, visible, and online, and retries on reconnect or when returning to the app after that interval. Saving runs quietly without an online save-status banner on the website or native apps. Existing live-score polling remains unchanged. Browsing The Wire, Stat Hub, and LIVEWIRE also saves their public responses. Offline browsing is read-only: private account data, favorites sync, sign-in, publishing, and new notifications require internet.

When disconnected, an offline banner warns that scores, game statuses, stats, odds, and projections are snapshots, not live updates. It shows the oldest saved response used on the current page when available and any offline-save errors. Other weeks, searches, filters, matchup-board projections, and older post pages still need to be opened online before going offline. Weekly player faces/logos are explicitly downloaded rather than relying on the browser's temporary image cache. Previously viewed public LIVEWIRE photos are also saved. Upstream missing stats or photos cannot be invented; unavailable requests, storage failures, or incomplete saves are logged. The Locker Room's private account history is not cached by this feature.

The website also writes successful public ESPN/post responses directly into device-local Cache Storage before returning them to the UI, without waiting for service-worker activation. Logos, faces, and public post photos are stored as readable image bytes and rendered from local blob URLs, avoiding a competing initial remote image request. These copies share the worker's bounded public/image stores; cold offline launches can reuse them, and failed refreshes never overwrite the last successful data. A failed scoreboard poll also retains the currently displayed games. Weekly warming saves team logos first and player images per matchup rather than waiting for the entire week's stats to finish. A missing image does not stop later image batches, and a failed team save does not skip its opponent; incomplete saves are still recorded as failures. The app requests persistent browser storage when supported, but browser eviction, clearing site data, private browsing, and content never downloaded cannot be covered. Live data is saved on each device, not committed into the source code; reconnecting resumes fresh ESPN reads.

Public API reads display a successful saved response first, without waiting for ESPN, then revalidate quietly online. Concurrent refreshes of the same query/format/filter share one request, with a 15-second minimum between checks to avoid update-triggered loops. Changed response bodies are saved before a batched notification refreshes the affected scoreboard, player/stat panels, news, LIVEWIRE feed, or matchup board. Unchanged responses do not trigger UI updates; existing stats stay visible during refresh and failed refreshes retain the last good copy. Native foreground reads likewise use a disk-only `peek` before background revalidation through the shared native store. Content not previously saved still needs its first download; reading local files and rendering are not literally instantaneous. Only ESPN feeds and the configured project's public LIVEWIRE/matchup-board reads are eligible. Authentication, role checks, private tables, RPCs, writes, and error responses are never cached. Theme/player filters and response formats keep separate cache keys. Public response storage is bounded to 1,500 requests (at most 5 MB each), with 2,500 runtime images to accommodate a full NFL week including defensive players rather than evicting faces after a few teams. Older entries are evicted. Image warming uses four concurrent downloads and game warming two concurrent games. New builds replace the shell cache without touching existing notification routing. Cached public responses may remain after sign-out because they are public. Phones do not guarantee background timers when the app is closed or suspended; no automatic refresh is promised in that state.

Reload/reopen once online after an update to install the new offline worker. Offline access requires a secure origin (HTTPS or localhost), service-worker support, and browser storage; private browsing, storage pressure, or device cleanup can remove saved content. Run `node --test scripts/offline.test.mjs scripts/notification-routing.test.mjs` to check cache rules, isolation, and notification behavior. To verify in a browser, use a production preview (`npm run build`, then `npm run preview`), load public views online, enable network offline mode, and reload. Vite development mode does not cache the development module graph.

For immediate repeat openings, successful loads also retain assembled public scoreboard, player-table, game-box-score, team-average, and roster-detail snapshots in local storage. The Wire and Stat Hub read these synchronously during rendering instead of rebuilding them through the full schedule/roster/history/player-request chain. They are keyed by feed, season, team/game, and selected week; saved totals stay visible if a refresh fails. Full-week warming starts after a five-second opening grace period to reduce startup contention. This additional display store is bounded to 160 entries, roughly 4 MB of UTF-16 text, and 256,000 characters per entry. Rosters are saved once per team/game, not duplicated for both single-team and combined views, and player-table snapshots retain only displayed players. It contains no authentication or private account data and is cleared on account deletion with late writes disabled. Existing installations need one successful load with this version to create assembled display snapshots; never-downloaded data still requires ESPN.

### Native iPhone and Android apps

The Capacitor projects in [`ios/`](ios/) and [`android/`](android/) bundle the React interface rather than loading the website remotely. Native tooling requires Node.js 22 or newer. Run `npm run native:sync` to build `dist-native` and copy it to both projects, then `npm run native:ios` (on a Mac with Xcode) or `npm run native:android` (Android Studio/JDK 21/SDK 36). Normal `npm run build` and GitHub Pages deployment remain separate. `us.gamewire.app` is the initial bundle/application identifier; confirm its availability under your developer accounts before signing or publishing.

Native `GameWireOffline` bridges use shared on-device files for successful public ESPN and public LIVEWIRE/matchup-board reads and sports/post images. Foreground reads, five-minute weekly saves, and background jobs access the same files; the image component resolves them through Capacitor's local file server. Cache keys preserve exact queries, Accept, and fantasy filters. Auth, private tables, RPCs, writes, bearer tokens, and cookies are not replayed or saved. Only the public API key is retained for anonymous public-table refresh. Native public caches are excluded from backups and bounded to 4,000 files/512 MB; eviction during a snapshot reports an incomplete save, and atomic writes preserve good copies on failed downloads. Account deletion clears native files and cancels scheduled refresh. Native WebViews do not use the web service worker.

Android WorkManager requests unique 30-minute periodic work, with internet and non-low-battery constraints. iOS registers `BGAppRefreshTask` at launch, declares only the `fetch` background mode, requests an earliest start 30 minutes later, and resubmits after each invocation. No audio, location, exact alarms, or silent-push tricks are used to keep the app alive. Both systems control execution and can defer or skip it; iPhone force-quit, disabled Background App Refresh, battery restrictions, and lack of connectivity can prevent updates. Reopening the native app online starts an immediate foreground snapshot regardless of the five-minute timer.

Background jobs incrementally replay previously saved public requests, prioritizing the current scoreboard then the oldest saved requests, with a ~24-second budget and a maximum of 48 requests per invocation, then download discovered missing ESPN images if time permits. They do not promise to refresh a whole NFL week within Apple's short execution window or fetch unseen weeks automatically. Successful responses replace individual copies; failures retain previous copies. Native refresh status retains last attempt, count, remaining requests/images, and incomplete-copy details for diagnostics without displaying an online banner. Foreground saving fills any gaps. A fresh install needs one successful online visit before there is a background request list.

Validation: `node --test scripts/native-offline.test.mjs scripts/offline.test.mjs scripts/notification-routing.test.mjs`; `npm run build`; `npm run native:sync`; Android `gradlew :app:assembleDebug :app:assembleDebugAndroidTest :app:testDebugUnitTest`; and an Xcode simulator build. With an Android emulator/device connected, run `gradlew :app:connectedDebugAndroidTest` for the isolated native-store tests (cached image file paths, retained stats after network failure, private-source rejection, and cache clearing). The manually dispatched [`Validate native apps`](.github/workflows/native-build.yml) workflow provides separate Linux/Android and macOS/iOS compilation without signing or publishing. Compilation alone does not prove OS scheduling: test physical iPhone and Android devices, background and cold-offline launches, disabled refresh, low battery, expired sessions, and deletion while refresh is running. In Xcode, use the registered `us.gamewire.app.public-refresh` task identifier to simulate launch/expiration while debugging; a real scheduling test must also be performed outside the debugger.

This is native background-refresh groundwork, not an App Store approval guarantee or submission-ready release. Before submission, configure signing/developer accounts, replace generated app icons/splash assets, verify data/photo/logo licensing, supply privacy policy and accurate App Privacy/Data Safety disclosures, complete the privacy-manifest review, test login/password-reset deep links, and implement APNs/FCM native push if notifications are part of the native listing (browser Web Push is deliberately disabled in native builds). Verify user-content moderation/reporting requirements for LIVEWIRE. Apple reviews minimum functionality and the entire app, not the presence of a background mode. Use TestFlight/internal Android testing before submitting; never advertise guaranteed 30-minute background updates.

## Accounts and favorites

### Permanent account deletion

Profile includes **Delete my account**, requiring the current password and an exact `DELETE` confirmation. The server independently verifies the session and password; it never trusts a user ID supplied by the browser. Deletion removes uploaded files (including unpublished photos) through the Storage API, then hard-deletes the auth user. A database trigger removes authored LIVEWIRE posts, and foreign-key cascades remove favorites, Locker Room history, roles, push subscriptions, queued deliveries, and deletion state. Shared weekly matchup boards remain with `updated_by` cleared. Losing the last owner account also removes its owner access; transfer/grant a replacement owner administratively before deleting if needed.

Apply [`supabase/account-deletion.sql`](supabase/account-deletion.sql) after the existing schemas, then deploy `delete-account` with `supabase functions deploy delete-account`. Its gateway JWT check is disabled because the function validates the bearer token itself with Auth `getUser`; service credentials stay server-side. Deletion preparation is service-role-only and pauses further uploads until deletion finishes. Storage failures retain the account for retry and are explicitly reported; already removed photos cannot be restored. Existing notification and read-only offline features continue unchanged.

After success, the current device clears GameWire preferences, runtime public caches, its push subscription, and local auth session. Cleanup failures are reported separately from successful server deletion. Copies already downloaded on other devices, notifications already delivered, and provider-managed backups cannot be instantly erased; backup removal follows the provider's retention policy. Offline copies are public, not account-private data. An account cannot delete itself offline.

Run [`supabase/tests/account-deletion.sql`](supabase/tests/account-deletion.sql) for rollback-only cascade/isolation/upload-guard tests, and `deno test --allow-env --allow-net supabase/functions/delete-account/index.test.ts` for mocked authentication, upload cleanup, hard deletion, and failure checks. Never test deletion with a real user account.

GameWire uses Supabase Auth for email/password accounts and stores each user's favorites in a row protected by row-level security.

1. Create a Supabase project and enable email authentication.
2. Copy `.env.example` to `.env.local` and set `VITE_SUPABASE_URL` and `VITE_SUPABASE_PUBLISHABLE_KEY` from the project API settings. The older `VITE_SUPABASE_ANON_KEY` variable is also supported.
3. Run [`supabase/schema.sql`](supabase/schema.sql) in the Supabase SQL editor to create the per-user favorites table and policies.
4. Set the Supabase Auth site URL and allowed redirect URLs to your local and deployed GameWire URLs.
5. Restart the Vite dev server.

Only a publishable or legacy anon key belongs in the frontend. Never expose a Supabase secret or service-role key.

Email/password signup is open with no application-imposed total-account cap. Signup email confirmation is disabled in [`supabase/config.toml`](supabase/config.toml), so creating an account signs the user in immediately without consuming the built-in email quota. This does not verify email ownership. Supabase abuse-protection rate limits and hosting/plan capacity still apply; these are not unlimited. Password-reset emails still use the configured email service and its quota. Configure production SMTP before relying on password recovery at scale or re-enabling confirmation. Apply the declared auth settings with `supabase config push` after reviewing its diff; avoid changing unrelated remote settings.

Locker Room **Latest updates** only shows team score checkpoints at completed quarters/overtime periods and at Final, not every scoring play or a mid-quarter snapshot. Quarter checkpoints use cumulative ESPN linescores, including scoreless quarters. If period data is unavailable, no quarter score is invented; final scores remain available. Existing granular score history is retained in storage but hidden from this feed. Latest plays, player-stat rows, live scoreboards, and push alert frequency are unchanged. Run `node --test scripts/locker-room-scores.test.mjs` to verify checkpoint generation.

### LIVEWIRE

Everyone, including guests and mobile app users, can filter LIVEWIRE by multiple themes. Selecting News and Fantasy shows posts with either theme, newest first. **All posts** clears the filters and includes untagged posts. Filtering happens in the database before pagination, so **Load older posts** retrieves older matching posts rather than filtering only the current page. A post opened by a notification/direct link remains visible even if it is outside the active filters, with an explanatory notice.

Admins can select any combination of **News**, **Fantasy**, and **Betting** in the post composer. Published posts display matching blue, gold, and purple badges beside the author/date, using the same styling as TNF/SNF/MNF game labels. Themes can be changed or cleared when editing. Existing posts remain untagged; older clients preserve tags when editing. Apply the updated [`supabase/livewire.sql`](supabase/livewire.sql) before deploying the frontend. Run [`supabase/tests/livewire-themes.sql`](supabase/tests/livewire-themes.sql) for rollback-only validation and compatibility checks.

Admins can attach up to four photos per post (JPG, PNG, WebP, or GIF; 5 MB each), preview/remove selections, and retain, replace, or remove photos while editing. Photos display in a responsive gallery and enlarge in an in-page modal. Titles and post text remain required. Apply the latest `supabase/livewire.sql` to create the public `livewire-photos` bucket, its admin-only upload policies, and the extended save RPC. Existing clients preserve attached photos when editing. Upload failures keep the draft and attempt cleanup of unused new files; cleanup failures are surfaced. Removed/published assets remain in storage for manual administrative cleanup to avoid breaking existing public links. Photos are public assets, not private uploads; do not upload sensitive content. Run `supabase db query --linked --file supabase/tests/livewire-photos.sql` for rollback-only attachment and upload-permission tests.

Admin posts have a required subject/title (up to 120 characters) above the 500-character body. The feed uses author initials, the public author name, a full local date/time, and a prominent headline, styled like Locker Room updates. Editing preserves both fields. Older untitled posts remain readable without an invented headline; editing them in the current interface requires adding a title. Apply the updated LIVEWIRE SQL before deploying this interface; the save RPC retains compatibility with older clients and preserves existing titles when an older client edits a post.

The top navigation includes a standalone public **LIVEWIRE** section between **Stat Hub** and **Locker Room**, separate from personal weekly history. Guests and members can read posts. Authorized admins can publish up to 500 characters with an optional HTTP/HTTPS news link and edit/delete their own posts. The owner can manage all posts and grant/revoke admin access for existing accounts by email using **Manage LIVEWIRE admins**. Verify intended admins' account identities out of band before granting access: signup does not verify email ownership. Posts refresh every 30 seconds, with older posts available through **Load older posts**. LIVEWIRE has no NFL week selector because this editorial feed is not filtered by week.

Apply [`supabase/livewire.sql`](supabase/livewire.sql) before deploying the frontend. A trusted database administrator must bootstrap the owner's `user_id`, `role = 'owner'`, and public `display_name` in `public.livewire_roles` after verifying the account identity. No owner is granted by signup, email entered in the browser, or editable account metadata. Role membership is private except to the owner; public posts store an author display name, not an email. Database privileges and security-definer RPCs enforce permissions even when the UI is bypassed. Revoking an admin prevents further writes immediately, while their published posts remain.

Run [`supabase/tests/livewire.sql`](supabase/tests/livewire.sql) through the SQL editor or `supabase db query --linked --file supabase/tests/livewire.sql` to verify guest/member access, posting validation, role escalation prevention, moderation ownership, and revocation. All test data is rolled back.

## Mobile push notifications

Profile shows a persistent **Notifications enabled** status when browser permission is granted and this device has a subscription saved for the signed-in account. It rechecks when returning to the tab/window; a failed status check is shown with Retry rather than claiming notifications are active.

LIVEWIRE notification links include the post ID (`#livewire/post/<id>`). The dispatcher sends an absolute production URL so older installed service workers retain the `/FOT/` path. Set the Edge Function secret `GAMEWIRE_SITE_URL` if moving to a different deployment (default: `https://mgtrabulsi-cell.github.io/FOT/`). The updated worker also normalizes legacy root-path alerts back into its own deployment scope and recovers LIVEWIRE post IDs from notification tags. It messages an existing app window instead of reloading it, preserving that window's signed-in session. A new window restores the normal saved session; if the user signed out, their session expired, or they disabled Remember this device and closed the tab, sign-in is still required and the post destination is retained. Linked posts are fetched even when older than the first feed page, scrolled into view, and highlighted; deleted posts show an unavailable message.

Game score/status and favorite-player play alerts use `#wire/game/<ESPN event ID>` and select that exact matchup on The Wire, clearing any game-search filter. The matchup is fetched directly from ESPN even if it belongs to a different week than the current game wheel. A failed lookup shows a Retry action rather than silently selecting another game. Legacy game/play notification tags also recover their matchup IDs. Test notifications open The Wire without a specific matchup.

Run `node --test scripts/notification-routing.test.mjs` to check post, game, player-play, and test notification routing for both new windows and existing signed-in windows.

Every newly published titled LIVEWIRE post queues a push to all devices with notifications enabled, independent of favorites or the score-alert checkbox. Its title uses the first theme selected in the composer: `FANTASY: <subject>`, `NEWS: <subject>`, or `BETTING: <subject>`. With no theme, it remains `LIVEWIRE: <subject>`. Selection order is preserved; removing and reselecting a theme moves it to the end. The first theme and subject are captured when publishing, so edits do not change pending alert titles or send another notification. The body is empty; post text is not included. Existing queued alerts without a captured theme retain the LIVEWIRE prefix, and old posts are not broadcast when this feature is installed. Apply the updated notification SQL and deploy `send-livewire-push` to activate this behavior. Tapping the alert opens the standalone LIVEWIRE section at the correct deployment base path. Browser/OS notification permission and delivery policies still apply.

After applying `livewire.sql`, deploy `send-livewire-push` and run [`supabase/livewire-notifications.sql`](supabase/livewire-notifications.sql). This uses the existing `gamewire-poll-url` and `gamewire-poll-secret` Vault entries and `GAMEWIRE_CRON_SECRET`/VAPID function secrets. The private delivery queue is processed every minute (typically the next minute after publishing), in batches of 100 with leased claims and retries for transient failures. Expired device subscriptions are removed. Delivery failures are recorded in `livewire_push_deliveries.last_error` and Edge Function logs. Push-provider acceptance is not a guarantee of device display; an interrupted send can be retried, with the post-specific notification tag replacing duplicate alerts where supported. Run [`supabase/tests/livewire-notifications.sql`](supabase/tests/livewire-notifications.sql) for rollback-only queue/permission tests.

Run `deno test --allow-env --allow-net supabase/functions/send-livewire-push/index.test.ts` to verify headline-only payloads, authorization, disabled-device handling, and retries against mocked providers (no real notifications are sent).

GameWire can send score and status changes for games involving a user's favorite teams or players. Push alerts require an HTTPS deployment; on iPhone, install GameWire from Safari's Share menu to the Home Screen before enabling notifications.

1. Re-run [`supabase/schema.sql`](supabase/schema.sql) in the connected Supabase project. It creates the per-device push subscription and private game-state tables.

## Score coverage

### Admin-curated favorable matchups

**Stat Hub → Favorable matchups** is a public weekly board, replacing the automatic above-allowance ranking. Existing LIVEWIRE owners/admins can search active NFL skill rosters beside the heading, select up to four players each at QB/RB/WR/TE, reorder each position with up/down controls, and remove picks. **Publish matchups** publishes the whole board atomically; draft edits are private until publication. **Discard changes / reload** returns to the current published board. Concurrent editors receive a conflict instead of overwriting another admin's publication. Selections persist by season and regular-season week and refresh every 30 seconds; weeks do not copy each other's picks.

Apply [`supabase/matchup-board.sql`](supabase/matchup-board.sql) after [`supabase/livewire.sql`](supabase/livewire.sql) and before deploying this frontend. The new table has public read-only access; only the role-checked RPC can publish, with a four-per-position limit, unique player IDs, and revision checks enforced in the database. Missing setup and load failures display errors rather than an automatic substitute list. Run [`supabase/tests/matchup-board.sql`](supabase/tests/matchup-board.sql) against a test database for rollback-only publication, permission, limit, ordering, and conflict checks.

Each selected player shows their position's main yardage average (QB passing, RB rushing, WR/TE receiving) from their own ESPN regular-season game log before the selected matchup, the opponent's season-to-date NFL yards defense rank, and ESPN's weekly projected PPR fantasy points. The average uses reported values from up to five recent games in the selected season, with its actual sample count shown; preseason, future games, and the selected matchup are excluded. Missing values do not become zeros or invalidate other reported games. Existing averages stay visible during refresh, with refresh failures reported separately. Players without any reported values show "No recorded games" rather than an invented average. ESPN's public fantasy default-PPR feed is queried for the selected player IDs, not its default first 50 players, and verified for one-point reception scoring. Projections must match season, scoring week, projected source, and weekly split exactly; season totals and actual scores are never substituted. The public response can omit players or projections: unavailable values stay unavailable, with feed failures shown separately. These projections are not guaranteed outcomes; defense ranks are not position-specific fantasy points allowed, and editorial selections are not confirmed starters. Run `node --test scripts/matchup-board.test.mjs` for data and ordering regression tests.

The scoreboard is currently focused on the NFL. Scores refresh every 30 seconds. The **Current** week advances at noon every Tuesday in **America/New_York (Eastern Time)**, using ESPN's regular-season calendar, even if ESPN's default scoreboard still shows the previous week. Open pages pick up the rollover on their next refresh. Manual week selections stay on the selected week; choosing **Current** restores automatic rollover. Outside the regular season, the default ESPN week is retained.

Before kickoff, The Wire's Team Comparison shows both teams' season-to-date regular-season points, total yards, passing yards, and rushing yards per game, plus the corresponding points and yards allowed per game. These values come from ESPN's team season statistics, not projections or player-specific matchup averages. Missing values are shown as unavailable, and failed requests have a retry action. Once a game starts, Team Comparison shows that game's box-score statistics.

The pregame Player Box Score shows one active QB ranked by recent passing attempts in Passing, only the top two active RBs by season rushing yards in Rushing, and only the top six active WRs/TEs combined by season receiving yards in Receiving, when available. All active RB/WR/TE candidates are checked before ranking season totals; recent usage does not pre-limit these candidates. These are statistical rankings, not confirmed starters. Switching to Avg stats preserves the same players and ordering. Total stats uses totals for the selected team and year; Avg stats divides those totals by each player's GP. Career totals, other seasons, and other teams' records are excluded. Missing values stay unavailable; failed player requests are reported with a retry action, so rankings may be incomplete when requests fail. Pregame tables do not include team-total rows. After kickoff, these limits do not apply: all players and categories reported by ESPN's game box score are available, refreshed every 15 seconds during live games. Team Comparison continues to show season per-game averages before kickoff. Stat Hub is unchanged.

The NFL Players area uses a draggable game wheel, then groups players by position and recent usage. Each team shows one usage-ranked QB, two RBs, one TE, and up to four WRs when those players have recent box-score usage. ESPN's public roster marks active status but does not provide an official depth chart, so starting roles are inferred from recent box-score participation.

Selecting an NFL game also opens team player lists and a trends view with the feed's current spread, total, moneyline, team scoring averages, and recent results. Selecting any listed player opens a game-by-game chart for their last five games with a draggable, scrollbar-free horizontal stat selector tailored to position: quarterbacks get passing stats, running backs get rushing and receiving stats, and receivers/tight ends get receiving stats. Values absent from a game feed are shown as unavailable. ATS history is displayed only when the feed includes it; this source currently omits those records for some matchups. The app presents information, not betting picks.

The ESPN feeds used here are public, undocumented endpoints with no availability or latency guarantee. For a production launch, use a licensed sports-data provider and confirm its coverage, terms, and update guarantees.

## Favorites and Your Locker Room

Run [`supabase/locker-room-history.sql`](supabase/locker-room-history.sql) once in the connected Supabase project's SQL editor (or with `supabase db query --linked --file supabase/locker-room-history.sql`). It adds account-isolated weekly history and an authenticated save function. The configured project has this migration applied.

Database regression checks are in [`supabase/tests/locker-room-history.sql`](supabase/tests/locker-room-history.sql). Run them with `supabase db query --linked --file supabase/tests/locker-room-history.sql`; all test users and rows are rolled back.

Locker Room follows the main NFL week selector. Collected score changes, matching headlines, big plays, and player game-stat snapshots are archived by account, season, and NFL week, with no Tuesday deletion of the archive. Signed-in history follows the account across devices; guests keep browser-only history. Player snapshots retain the player's identity even if they are later unfavorited. Save/load failures are visible with a retry action, not a silent browser-only fallback for accounts.

The Following > Players section shows a compact game-stat row: WR/TE receptions/targets, receiving yards and receiving TD; RB rushes, rushing yards and rushing TD; QB completions/attempts, passing yards, passing TD and interceptions. Live stats refresh every 15 seconds while the site is open; completed-game stats remain saved and are labeled FINAL. Returning to a previous week loads its saved activity and can retrieve available final ESPN stats and qualifying plays for current favorites. Older headlines and score-change sequences deleted before this feature cannot be reconstructed; past final scores and ESPN plays are not a complete replay of deleted updates. Missing feed values remain unavailable rather than being filled with zero. Loading and refresh failures are shown explicitly. Pregame games do not show a game-stat row.

Favorite a team from its game center or a player from their stats popup. Once signed in, favorites are saved to that user's Supabase account. Your Locker Room combines ESPN headlines matched to favorite names with score/status changes and big-play alerts for favorited NFL players. Scoreboards poll every 30 seconds, latest plays every 15 seconds during relevant live games, and news every five minutes. ESPN public feeds have no availability guarantee.
